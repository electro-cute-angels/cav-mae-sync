1. The pipeline (offline → online)
There are three offline stages that feed the live web app:

Extract (extract_embeddings.py) — runs CAV-MAE Sync over every segment and writes 4 tensors per segment into the memmapped store under embeddings/. Each segment = 16 frames spanning ~10 s.
Index (build_index.py) — reduces the per-frame cls embeddings into compact, L2-normalised search indices under index.
Serve (server.py + retrieval_engine.py) — loads the indices into RAM and answers search/localization requests; app.js is the 3-column UI.
2. What's stored per segment
From cavmae_common.py (forward_features):

array	shape	meaning
cls_audio	(16, 768)	per-frame audio summary vector
cls_video	(16, 768)	per-frame visual summary vector
patch_audio	(16, 208, 768)	per-frame audio patch tokens
patch_video	(16, 196, 768)	per-frame visual patch tokens
196 visual patches = a 14×14 spatial grid over the 224×224 frame (16-px patches).
208 audio patches = an 8 × 26 grid over the spectrogram: 8 frequency bands × 26 time steps (the 4 s audio window is 416 mel-frames → 416/16 = 26 time patches, 128 mel bins → 128/16 = 8 frequency patches). I confirmed the ordering in the model (forward_feat transposes to freq-height then Conv2d.flatten(2)), so token index i → (freq = i // 26, time = i % 26).
The cls_* vectors are the "what does this frame sound/look like" summaries; the patch_* tokens are the fine-grained "where in the image / where in the spectrogram" tokens.

3. The search indices
build_index.py produces two granularities:

clip vectors clip_audio/clip_video (N, 768): mean-pool the 16 per-frame cls vectors, then L2-normalise → one vector per segment. A whole-corpus search is a single matrix multiply.
frame vectors frame_audio/frame_video (N, 16, 768): each frame's cls L2-normalised, kept for the "sync" re-ranking strategies.
4. How a query runs
In retrieval_engine.py search():

direction picks which modality is the query and which is the database:
audio2video: the segment's audio clip vector is matched against every segment's video clip vector → "find frames that match this sound."
video2audio: reverse → "find sounds that match this image."
A first pass scores all N segments with db_clip @ q_clip (cosine, because everything is L2-normalised).
Filters: exclude_parent drops every segment from the same source film (so you don't just retrieve neighbouring clips of the same movie); video2audio also drops silent segments (their audio is synthesised/meaningless as a target).
If the strategy isn't fast, the top candidates are re-ranked on the 16 per-frame vectors.
Uploads (server.py retrieve_upload) encode a new image/wav on the fly via encode_media and do the same clip-vector matmul.

Two small implementation notes if you want it:

The engine currently only lazy-loads cls_audio and patch_video. For the audio map it needs cls_video (already on disk as cls_video.npy) and patch_audio (patch_audio.npy) — both exist, just add two more lazy-mmap properties.
The UI would need a spectrogram image to overlay onto. You don't currently render/serve the spectrogram, so either generate it from the wav on demand (server side, like the frame overlay) or display the 8×26 heat as a standalone strip aligned under the audio player.
